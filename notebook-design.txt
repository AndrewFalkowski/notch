Notch — Design Spec
===================
2026-06-24, updated 2026-11-24 (0.2: shared notebooks)


OVERVIEW
--------
Notch is a CLI lab notebook for humans and agents. Plain text files, human-readable
and editable, grep-able, with optional conveniences layered on top. The
canonical notebook is always the daily text files; indexes and UIs are helpers.
Emphasis on simplicity.

Agents are the main readers. Features should reduce how much an agent must
read to catch up (headlines, backlinks, digests) rather than add structure
the writer has to manage.


STORAGE
-------
Notebook location: NB_DIR, else "notebook" in ~/.config/notch/config.toml
(written by "notch setup"), else ~/Documents/notch-notebook/.

The notebook is separate from the Notch source repository and is usually a git
repository shared by several people.

Directory layout:

  ~/Documents/notch-notebook/
    entries/
      andrew-melchior-8ec2/
        2026-11-24.txt   ← one file per machine per UTC day
      sam-laptop-41c0/
        2026-11-24.txt
    notch.toml           ← shared settings (min_version), committed
    .gitignore           ← .index/, .notch.lock, .machine-id
    .machine-id          ← this machine's ID; never synced
    .notch.lock          ← write lock; contents unused
    .index/              ← optional generated cache; safe to delete

Each machine writes only its own entries/<machine-id>/ folder, so no file is
ever written by two machines and git never merges entry text. Readers take
the union of all folders and order entries by (date, time).

Notch 0.1 kept all machines' entries in shared YYYY-MM-DD.txt files at the
notebook root. Notch still reads those, and "notch migrate" moves them into
per-machine folders. Shared files cannot be synced safely: two machines
appending to one file conflict on every pull, and git's union merge keeps the
"---" separator lines only once, which folds one entry into another
(notch-20261124-melchior-8ec2-001).


ENTRY FORMAT
------------
Each entry starts with "---" written by the CLI. The metadata line is generated
from CLI flags. An optional git line follows it. The body is free-form prose
and may include tables, code, lists, Markdown, and lines containing "---".

Parser rule: a line exactly equal to "---" starts a new entry only when the
next line matches the metadata format. This lets bodies contain ordinary
Markdown separators without corrupting the notebook. When writing, the CLI
prefixes "> " to any body line that matches the metadata format and follows a
"---" line, so a quoted entry stays inside the entry that quotes it.

  ---
  [14:32] andrew | skewGP-20260624-luna-003 | skewGP | finding | exp3, sGP
  git: skewGP main@4f2a9c1
  Posterior alpha mass is bimodal at low lambda — not a convergence failure.
  The skew distribution has two modes at this SNR. Confirmed disappears
  above lambda 1.4 across 3 seeds.

  ---
  [14:47] claude | skewGP-20260624-luna-004 | skewGP | result | exp3
  git: skewGP main@4f2a9c1 dirty
  model: claude-opus-5-5
  RMSE comparison across lambda values (n=50, 10 replicates):

    lambda  | gGP   | sGP   | delta
    --------|-------|-------|------
    0.5     | 0.412 | 0.398 | -0.014
    1.0     | 0.387 | 0.341 | -0.046
    1.5     | 0.361 | 0.298 | -0.063

  ---
  [15:10] andrew | espresso-20260624-luna-001 | espresso | note | roast-curve
  15g dose, 93C, 28s pull. TDS 9.2 — brighter than yesterday's 30s shot.
  Probably under-extracted. Try finer grind tomorrow.

Metadata line fields (in order):
  [HH:MM]  author  |  ID  |  project  |  type  |  tag1, tag2, ...

[HH:MM] is UTC, and the file's date is the UTC date. Entries written by notch
0.1 used the writer's local time and date.

Field constraints:
  project   letters, numbers, "_", and "-"; no spaces or slashes.
            Case-insensitive: "add" reuses the most-used existing spelling,
            and search ignores case.
  author    letters, numbers, "_", and "-"; usually a person or agent name
  type      one of the entry types below
  tags      comma-separated short labels; no commas inside a tag.
            Case- and separator-insensitive ("nca_style" = "NCA-style"):
            "add" reuses the most-used existing spelling and drops repeats,
            and "search --tag" ignores the difference.

Optional "key: value" lines, in this order, between the metadata line and the body:

  git: <repo> <branch>@<short sha> [dirty]
  model: <model ID>            e.g. claude-opus-5-5; agents pass --model
  covers: <ISO week>           digests only

Git line (written automatically):
  Records the git checkout "notch add" runs from: the repo name as its origin
  remote spells it (so every clone agrees; else the directory name),
  branch ("detached" if none), HEAD, and "dirty" when tracked files have
  uncommitted changes. Omitted outside a git checkout and inside the
  notebook's own repository. HEAD is the commit before any uncommitted work,
  so agents should commit before logging code work.

Compatibility: new metadata goes on its own "key: value" line under the
metadata line, never as a new metadata-line field. Older installs then read
it as body text instead of rejecting the entry. Parsers skip entries whose
metadata line is malformed (bad type or tag) rather than failing.

First line of the body: by convention a one-sentence headline stating the
result or decision. "search --brief" shows only this line.


ENTRY TYPES
-----------
  note      general observation or thought
  result    quantitative output, table, numbers
  todo      something to investigate or return to
  question  unresolved, open, needs an answer
  status    where things stand on a thread or project
  finding   qualitative conclusion or insight
  digest    weekly project summary (see WEEKLY DIGESTS)


ENTRY IDs
---------
Format: <project>-<YYYYMMDD>-<machine>-<NNN>
  e.g.  skewGP-20260624-luna-003
        espresso-20260624-luna-001

Each machine gets a stable machine ID, generated once and stored in
.machine-id: the user's name, the sanitized hostname, and a short random
suffix (e.g. andrew-melchior-8ec2), so an ID shows whose machine wrote it.
"notch setup --name" replaces an ID that does not start with the name; old
entries keep their IDs. 0.1 IDs have no name (melchior-8ec2). It uses letters, numbers, "_", and "-". .machine-id must not
be synced between machines (keep it in the notebook's .gitignore), or two
machines would share an ID.

Per-project, per-day, per-machine counter. Counter is derived at write time by
counting existing entries for that project/date/machine in the machine's file
for that day. No
counter files or database state are kept. The ID format allows three digits,
so a counter above 999 on one day is not supported.

The CLI holds an exclusive file lock while assigning the ID and appending
the entry. This prevents duplicate IDs for concurrent writers on the same
machine. The machine ID prevents routine collisions when syncing notebooks
across multiple computers.

IDs encode when an entry was made and are self-describing when referenced
anywhere.


REFERENCES
----------
Cross-references go in the body as plain IDs:
  "See skewGP-20260624-luna-003 — bimodality confirmed above lambda 1.4."

Backlinks are computed when read, never stored: "notch show ID" scans the
notebook for later entries that cite ID and ends with

  -> referenced by: skewGP-20260625-luna-001 (finding), ...

so old entries gain backlinks without being edited. Entries are never
rewritten. A correction, closure, or follow-up is a new entry whose first
line names the old one ("Corrects <ID>: ...", "Closes <ID>: ...",
"Follows <ID>: ..."), and the old entry's backlink points readers to it.

Grep to find an entry and all references to it:
  grep -r "skewGP-20260624-luna-003" ~/Documents/notch-notebook/


AUTHOR MARKERS
--------------
Human entries:  first field is the user's name (e.g. "andrew")
Agent entries:  first field is "claude" (or agent name), plus a model: line
Set by --author, then NOTCH_AUTHOR, then "claude" when running inside Claude
Code (CLAUDECODE=1) without a terminal, then the configured name, then the OS
user name. The model comes from --model or NOTCH_MODEL; "add" reminds known
agent authors (claude, codex, ...) that leave it out. The machine segment of
the ID says whose machine (and so whose agent) wrote the entry.


GREP PATTERNS
-------------
All entries for a project:
  grep -r "| skewGP |" ~/Documents/notch-notebook/

All findings ever:
  grep -r "| finding |" ~/Documents/notch-notebook/

All human entries:
  grep -r "andrew |" ~/Documents/notch-notebook/

All entries with a tag:
  grep -r "exp3" ~/Documents/notch-notebook/

All entries made at a commit:
  grep -r "@4f2a9c1" ~/Documents/notch-notebook/

Entry + body (5 lines):
  grep -rA5 "| espresso | finding |" ~/Documents/notch-notebook/


GIT SYNC
--------
A notebook with a git remote syncs automatically; one without stays local.

  notch sync
         Under the write lock: stage and commit entries/<this machine>/ only,
         "git pull --rebase --autostash", then push. Pulls cannot conflict,
         because no other machine touches this machine's folder. On any
         failure it aborts a half-done rebase and reports git's error line.
         GIT_TERMINAL_PROMPT=0, so it never waits for credentials. The
         result and time go in .git/notch-last-sync.

When it runs:
  - after "notch add" (and the TUI): a detached background "notch sync"
  - at "notch catchup": in the foreground, if the last attempt is over an hour old
  - around digests: "digest-prep" and "add --type digest" sync first and
    refuse if that fails; the digest is pushed right after it is written
A failed sync shows as a notice at the top of the next catchup.
NOTCH_NO_SYNC=1 turns automatic syncing off.

Shared files (notch.toml, .gitignore) change rarely and are committed by
"notch setup". Edit them by hand like any repo file.


CLI INTERFACE
-------------
Built in Python. Distributed as a uv tool, available globally as "notch":
  uv tool install git+https://github.com/AndrewFalkowski/notch
From a local checkout (development):
  uv tool install --force --reinstall-package notch .

Commands:

  notch
         Full-screen Textual entry form (same as "notch tui"). Offers to
         update the install first if the local source is newer. Without a
         terminal (an agent's shell) it prints help instead.

  notch cli
         Prompt-based entry flow with numbered menus and a save preview.

  notch setup [--name NAME] [--notebook PATH] [--clone URL]
         Set up this machine (see SETUP). Flags only, so an agent can run it.

  notch add [--project P] --type finding --tags exp3,sGP [--model M] --entry "..."
         Write an entry to entries/<machine>/<UTC date>.txt and print its ID.
         Inside a repo, --project defaults to the project logged from it.
         "--entry -" reads the text from stdin. Without --entry: opens
         $EDITOR at a terminal, otherwise reads stdin (so an agent never lands
         in an editor). Notes on stderr when the project name is new, listing
         recent projects, to catch typos. Refuses when the notebook's
         min_version is newer than the install. (--message is a hidden
         legacy alias.)

  notch search [WORDS...] [--project P] [--type T] [--tag T]
               [--since 7d|2026-11-16] [--limit N] [--brief]
         Entries matching all filters, oldest first. WORDS must all appear
         (any order, case-insensitive). --limit keeps the N most recent
         matches. --brief prints the metadata line and first body line.
         Full output is capped at the 20 most recent matches unless --limit
         is given, with a note saying how many there were; --brief is not
         capped.

  notch catchup [PROJECT] [--limit N]
         Notices (sync failure, updates, setup), then the latest digest in
         full, metadata + first line of every entry since (at most N, default
         40), the project's 15 most used tags, then undigested weeks. Without
         PROJECT, uses the project logged from the current repo; if there is
         none, tells the agent to ask the user whether to start one.

  notch projects
         Each project with its entry count, last date, repos, and authors.

  notch ignore [--undo]
         Stop (or resume) catchup offering to log the current repo. Stored
         per machine in config.toml.

  notch digest-prep PROJECT WEEK
         Material and instructions for one digest (see WEEKLY DIGESTS).

  notch show ID [ID ...]
         Print entries by ID, each followed by its backlinks. Exits 2 if any
         ID is missing, after printing the rest.

  notch today
         Today's entries (UTC date) from every machine.

  notch sync
         Commit, pull, and push now (see GIT SYNC).

  notch info
         Version, notebook dir, config, author, machine ID, last sync, the
         update command, and notices.

  notch update-check
         Print notices; at a terminal, offer to reinstall from a newer local
         source checkout.

  notch guide
         Print the agent conventions (the packaged skill, without frontmatter).

  notch migrate
         Move 0.1 root-level daily files into entries/<machine>/, splitting
         each by the machine segment of its entry IDs. Checks that the set of
         entry IDs is unchanged before deleting anything, then commits.


SETUP
-----
"notch setup" makes one machine ready, and rerunning it is safe:
  - clone the shared notebook (--clone) or use/create a directory
  - write ~/.config/notch/config.toml: notebook path and name
  - make the machine ID start with the name
  - add the notebook's .gitignore lines and notch.toml (min_version = this
    version) if missing, and commit them
  - point out 0.1 root-level files that "notch migrate" should move
  - install the packaged skill to ~/.claude/skills/notch/SKILL.md
  - add a marked block (<!-- notch:begin --> ... <!-- notch:end -->) to
    ~/.claude/CLAUDE.md, and to ~/.codex/AGENTS.md if ~/.codex exists; reruns
    replace the block and leave the rest of the file alone
  - run a test sync, then print a short explanation of how notch works


UPDATES
-------
Notch never installs anything itself. It prints a notice with the exact
command, and the skill tells agents to ask the user before running it.
Notices appear at the top of "catchup" and in "info":
  - the notebook's notch.toml min_version is newer than the install ("add"
    also refuses to write)
  - for a git install, the remote's commit differs from the installed one
    (git ls-remote, at most once a day, cached in ~/.cache/notch/;
    NOTCH_NO_UPDATE_CHECK=1 turns it off)
  - a local source checkout is newer than the install
  - this machine is not set up, or its installed skill differs from the
    packaged one
The update command reinstalls and then runs "notch setup", so the skill and
global instructions move with the version. Raise min_version in notch.toml
when a release changes the notebook format.


TUI
---
Textual form: project list (recent projects, or a new one), type,
tags, entry editor, save. Writes entries identically to "notch add".


WEEKLY DIGESTS
--------------
A digest summarizes one project's completed ISO week so agents can catch up
without reading every entry. It is an ordinary entry of type "digest" with a
"covers:" line instead of a git line:

  ---
  [09:10] claude | skewGP-20260706-luna-001 | skewGP | digest |
  covers: 2026-W27
  Digest skewGP 2026-W27: bimodality is real below lambda 1.4 (skewGP-20260630-luna-002).
  State:
  - ...

Each digest builds on the previous one: State and Open are carried forward and
updated, so the latest digest alone gives the project's standing. Digests are
written oldest week first, never for the current week, and never rewrite
entries; corrections they find are listed as "<new ID> corrects <old ID>".
A week can be digested from the Wednesday (UTC) after it ends, so every
machine has had two days to sync its entries. "add --type digest" syncs first
and refuses a second digest for a week unless --replace is passed (another
machine may have written one); if two still cover a week, the later wins.

Writing is on demand rather than scheduled. "notch catchup" reports completed
weeks with entries but no digest; the reading agent hands them to a background
sub-agent (or tells the user) instead of interrupting its task. Notch never
calls an LLM itself.

  notch digest-prep PROJECT WEEK
         Prints the writing instructions, the save command, the previous
         digest, and the week's entries in full. Refuses if an earlier week
         still lacks a digest.

  notch add --type digest --covers WEEK ...
         Requires a completed week and rejects a digest that cites IDs that
         do not exist. Reports the length without cited IDs (target: under
         2,500 characters). "--entry -" reads the text from stdin.

Installs from before digests skip digest entries, since the type is unknown
to them.


LLM INDEXING (OPTIONAL, NOT IMPLEMENTED)
---------------------------------------
Optional search acceleration only, for semantic search. Writes embeddings or
other cache files to .index/. The notebook works completely without it, and
.index/ may be deleted at any time without data loss.


AGENT SKILL
-----------
src/notch/SKILL.md is the single source of the agent conventions. It ships in
the package; "notch setup" installs it for Claude Code and "notch guide"
prints it for other agents. It teaches agents to:
  - catch up with "notch catchup" in the repo, then "show" only the relevant IDs
  - relay notices, and run update commands only with the user's OK
  - ask the user before starting a project for an unlogged repo
  - hand undigested weeks to a background sub-agent via "digest-prep"
  - write entries headline-first and concise (writing-style rules)
  - run "notch add" from the repo the entry is about, with --model
  - cite IDs, and open corrections/closures with "Corrects/Closes <ID>:"
  - never edit existing entries
